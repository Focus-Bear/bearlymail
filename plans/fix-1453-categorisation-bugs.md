# Plan: Fix #1453 — QA passed miscategorised + debug category shows None

## Bug 1: QA passed email miscategorised as "QA failed issues"

### Root Cause

The categorisation prompt (`prioritise-email.md`) receives a **pre-summarised body** when one exists. The flow is:

```
llm-processor.ts L199:
  bodyForPriority = email.summary?.trim()
    ? email.summary                          // ← summary used if available
    : cleanEmailContent(email.body, ...)     // ← raw body (1000 chars) as fallback
```

The same pattern exists in the batch path (`llm-priority-batch.service.ts` L286).

The summary is generated by `summarize-email-tldr.md`, which says "Be brief and capture the key points" but has **no instruction to preserve QA pass/fail verdicts**. A QA email with body "QA Status: PASS — 5/5 scenarios passed" could easily be summarised as:

> "QA test results for 5 scenarios on GitHub issue #1234"

Without the word "PASS", the categorisation LLM sees both "QA failed issues" and "✅ QA passed issues" in the category list and has to guess. Since "QA failed" may be more common/salient, it defaults to that.

The categorisation prompt itself has **correct and explicit rules**:
> QA comment = PASS → use "✅ QA passed issues"  
> Pass signals: "QA passed", "✅", "verified", "working correctly", "ready for production"

But these rules are useless if the summary has already stripped out the pass/fail signal.

### Fix

**Two-part fix (belt and suspenders):**

#### Fix 1a: Preserve QA verdict in summaries (`summarize-email-tldr.md`)

Add to the summary prompt guidelines:

```markdown
## QA / Test Result Emails
When summarising QA or test result emails, ALWAYS preserve the pass/fail verdict explicitly.
Include the exact status (PASS/FAIL/PARTIAL) in the summary text. Example:
- ✅ "QA PASSED: All 5 test scenarios passed for issue #1234"
- ❌ "QA FAILED: 2 of 5 test scenarios failed for issue #1234"
Never omit the verdict — downstream categorisation depends on it.
```

Also add the same guidance to `incremental-summary.md` (for thread updates) and `summarize-email-bullets.md`.

#### Fix 1b: Prefer raw body for QA-like emails (optional, stronger fix)

In `llm-processor.ts` and `llm-priority-batch.service.ts`, when the email subject or body contains QA-related keywords (e.g. "QA Status", "QA passed", "QA failed", "test result"), **always use the raw body** (via `cleanEmailContent`) instead of the summary for categorisation. This ensures the categorisation LLM sees the actual verdict regardless of summary quality.

```typescript
// In both llm-processor.ts and llm-priority-batch.service.ts:
const isQaRelated = /QA\s*(Status|pass|fail|result)/i.test(email.subject || '') ||
                    /QA\s*(Status|pass|fail|result)/i.test(email.body?.substring(0, 500) || '');
const bodyForPriority = (!isQaRelated && email.summary?.trim())
  ? email.summary
  : cleanEmailContent(email.body, email.htmlBody, BODY_PREVIEW_LENGTHS.CLASSIFICATION_PREVIEW);
```

**Recommendation:** Implement both 1a and 1b. Fix 1a is the systemic fix (better summaries). Fix 1b is the safety net for this specific high-impact case.

- `server/promptfoo/prompts/incremental-summary.md` — add QA verdict preservation rule

## Bug 2: Category debug panel shows "None" despite email being categorised

### Root Cause

**Server/client field name mismatch.** The server's `EmailDebugCategoryService.getCategoryDebugData()` returns:

```typescript
thread: {
  categoryId: thread?.categoryId || null,        // UUID
  categoryExplanation: thread?.categoryExplanation || null,
}
```

But the client's `CategoryDebugData` type expects:

```typescript
thread: {
  category: string | null;           // ← expects display NAME, not UUID
  categoryExplanation: string | null;
}
```

The client renders:
```tsx
// CategoryDebugPanels.tsx — CategorySection component
{thread.category || <span style={emptyStyle}>{t('priority.categoryDebug.none')}</span>}
```

Since the server sends `categoryId` (UUID) but the client reads `thread.category` (which is `undefined` because the key doesn't match), it always shows "None".

This was introduced by the #1293 denormalization removal, which changed the server to return `categoryId` instead of the old `category` name field, but the client type wasn't updated to match.

### Fix

**Resolve the UUID to a display name on the server side.** The `categoryId` is a FK to `UserContext` where `contextKey = EMAIL_CATEGORY`. Look up the matching `UserContext` record and extract the category name from `contextValue`.

```typescript
// In email-debug-category.service.ts getCategoryDebugData():
const categoryContext = thread?.categoryId
  ? contexts.find(c => c.id === thread.categoryId && c.contextKey === ContextKey.EMAIL_CATEGORY)
  : null;
const categoryName = categoryContext
  ? categoryContext.contextValue.split(' - ')[0].trim()
  : null;

return {
  // ...
  thread: {
    category: categoryName,    // ← human-readable name
    categoryExplanation: thread?.categoryExplanation || null,
  },
  // ...
};
```

The `contexts` array is already fetched in the same method, so no extra DB query needed.

Also update the server-side `CategoryDebugData` interface to use `category: string | null` instead of `categoryId: string | null` so the types match the client.

### Files to modify
- `server/src/emails/email-debug-category.service.ts` — resolve categoryId → category name, update interface
